# 认证模型

本文档说明网站的登录鉴权机制：浏览器、桌面端与命令行三种场景如何携带凭据。

---

## 1. 总体原则

后端 `app/api/me/route.ts` **只认请求头** `Authorization: Bearer <微软 access token>`，
再用该令牌调用 Microsoft Graph `/me` 校验有效性并取回用户资料，最后结合数据库返回 `{ me, allProducts, products }`。

后端不区分令牌来自哪里——无论是浏览器 MSAL.js 登录，还是桌面端 / 命令行注入，只要令牌有效即视为已登录。

---

## 2. 浏览器场景

`AuthProvider`（`app/components/AuthProvider.tsx`）使用 MSAL.js：

1. 点击「登录」走 `loginRedirect`（PKCE）；
2. 回跳后 `handleRedirectPromise()` 换取 access token；
3. 拿到令牌后自动带 `Authorization: Bearer` 请求 `/api/me`。

相关配置见 `app/lib/auth/msalConfig.ts`，变量 `NEXT_PUBLIC_MICROSOFT_CLIENT_ID` 与 `NEXT_PUBLIC_REDIRECT_URI`（见 [环境配置](./环境配置.md)）。

> 必须使用 `localhost` 或 `https` 访问，否则 `crypto.subtle` 不可用（非安全上下文），会报 `crypto_nonexistent`。

---

## 3. 桌面端 / 命令行场景

Steam Sda 桌面端（C# / WPF WebView2）与命令行版会在网络层注入请求头：

- `Authorization: Bearer <MSAL.NET 获取的 access token>`
- `machine-code: <设备机器码>`（用于可选的机器码绑定校验）

因此客户端内打开网站时 **无需再次授权**，网站侧发请求即可被识别（无需写 localStorage）。

> 本项目与桌面端 steamsda 共用同一个 Azure 微软应用注册，桌面端注入的 scope 为 `user.read`，
> 浏览器端为 `User.Read`——同应用同租户（`consumers`），后端均可校验通过。

---

## 4. 机器码绑定

- 设计上，桌面端携带 `machine-code` 头调用 `/api/me` 时，后端会查 `machineBinding` 表做绑定校验，未绑定则拒绝。
- **当前状态：该校验已临时关闭**（线上 `machineBinding` 表尚无绑定记录，而桌面端必然会注入该头，开启会导致请求全部 401）。
- 校验代码已在 `app/api/me/route.ts` 中注释保留，待机器码绑定流程补齐后再启用。

---

## 5. AuthProvider 探测逻辑（重要）

前端 `AuthProvider` 使用 **统一的 `probe()`** 而非拆成多路：

1. 优先用浏览器 MSAL 静默 token 带 `Authorization` 头请求 `/api/me`；
2. 拿不到 token 就「裸发」请求（依靠 C# 注入的头）；
3. 任一成功即 `setMe`。

`me` 只能有一处来源，若拆成「裸探测 + accessToken 驱动」两处，桌面端场景（浏览器 MSAL 无 token）会失配、刷新后产品列表空白。

触发 `probe` 的时机：`initialized` 完成后，以及每次 `accessToken` 变化（覆盖登录回跳、刷新恢复、桌面注入三种场景）。
